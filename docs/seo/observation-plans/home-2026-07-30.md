## 0. The three categories of movement (review discipline)

Every Delta review of this experiment classifies each observed change into
exactly one category before interpreting it:

1. **By-construction changes** — expected because of how the engine works.
   The page changed, or the engine recalculates on a fresh run. Never
   evidence for or against the hypothesis.
2. **Experimental outcomes** — the metrics actually under test (§3).
3. **External effects** — Google algorithm changes, query-mix shifts,
   NewsTicker rotation, indexing behavior, seasonality. Logged as
   confounders (baseline §6).

Two questions every future baseline must answer before implementation:

- *What metrics are expected to change because the page changed?*
- *What metrics are expected to change because the engine recalculates?*

Those are not the same thing.

**Expected engine effect (freshness reset) — pre-registered, then falsified
at check 0.** The baseline predicted Priority would rise ~4–5 points on the
first post-edit run from the freshness factor resetting, with the standing
rule: *this is not evidence supporting the hypothesis and must not be
interpreted as experimental success.* Check 0 showed the reset **does not
fire**: the engine derives `lastModified` from git commit dates of a page's
`sourceFiles`, and a static route's sourceFiles is only its route file
(`src/pages/index.astro`). This experiment edited
`src/components/content/HomePage.astro` and the i18n JSONs — invisible to the
freshness tracker — so Priority stays 77 and `ageDays` keeps counting from
2026-07-01. The engine's freshness is now *understated* for `/`; if a
freshness-attribution fix (tracking component/i18n dependencies) ships later,
Priority will move **at that moment** — an engine artifact to be logged in §6,
never evidence. ~~Priority will jump ~4–5 points~~ — see erratum 3 below: the
direction of that claim was also wrong. Opportunity (76) is derived from GSC data only,
did not move at check 0 (verified), and is expected to *fall* if the
experiment succeeds (proximity band exits below position 5; baseline §2
interpretation trap).

**Baseline errata (recorded at check 0; the baseline file is immutable and
keeps its original text):**

1. Baseline §4 predicted `aiGap` would clear at AI readiness 67 ("aiGap floor
   is below 67"). The floor is **70** (`THRESHOLDS.aiReadinessFloor`,
   `scripts/seo/config.mjs`), so `aiGap` correctly **remains set** at 67.
   Clearing it requires further AI-readiness work (schema/tables/definitions/
   insights) that is deliberately deferred until after this experiment.
2. Baseline §5 expected `lastModified`/freshness to reset on both routes; per
   the sourceFiles gap above, it resets on neither.
3. **Added 2026-07-30, during EXP-003 screening.** The baseline's freshness
   prediction was wrong in *direction*, not only in whether it fires. It
   pre-registered "Priority is expected to increase by ~4–5 points due solely
   to the freshness factor resetting." The engine computes
   `freshness = clamp01(ageDays / 365)` (`scripts/seo/score.mjs`, weight 5) —
   a **staleness** factor: an older page scores *higher* because it needs
   refreshing. At the baseline's 28 days the factor was 0.077, worth 0.38 of
   5 points. A reset to age 0 therefore *removes* ~0.4 points; it can never
   add 4–5, and the full 5 points accrue only at 365+ days. So had the reset
   fired, Priority would have fallen ~0.4, not risen. This correction changes
   no experimental metric — Priority is context, never a judged outcome — but
   it retires a wrong engine model before any Delta review could reason from
   it. EXP-003 pre-registers the corrected behaviour as a positive control:
   its edited file *is* in `sourceFiles`, so freshness must reset there and
   Priority must fall ~0.33 (see that baseline §5).

## 3. Success thresholds (pre-registered, baseline §8)

Tighter than /medigap's because 15× volume makes smaller deltas real.

| Verdict | Criteria (post-change-only window, impressions read alongside) |
|---|---|
| **Supported** | Average position ≤ 5.0 (top-5 entry from 7.15) with impressions flat or up |
| **Directionally supported** | Improvement ≥ 1.0 position (≤ 6.15), not top-5 |
| **Not supported** | Movement < 1.0 in either direction after 8 weeks |
| **Regressed** | Position worsens ≥ 1.0, or impressions fall >30% while site-wide impressions are flat/up |

**CTR promotion rule:** the homepage's 23 clicks are the site's largest
single-page click base, but one page does not clear the CTR-confidence bar
(~10 pages with ≥10 clicks). If the bar is reached mid-experiment, CTR may be
promoted to a judged secondary metric **by an explicit §6 log entry, never
retroactively**.

## 4. What this experiment can and cannot conclude

This is the Pattern Ledger's first **isolated** experiment: exactly one
pattern (Standard AI summary), exactly one page.

Can conclude (if supported): adding the standard AI summary to a
striking-distance, high-volume page with an extractability deficit improves
average position — an isolated data point for the **Standard AI summary**
pattern, satisfying graduation criterion #2 for that pattern.

Cannot conclude: anything about the other five patterns; that the result
generalizes to low-volume or deep pages (this is the depth-0, nav-saturated
homepage — an archetype of one); anything about CTR or clicks.

**Attribution rule (baseline §6):** if a confound of type 2–5 (NewsTicker
rotation, sitewide template change, inbound-link drift, unreconciled
auto-commits) materially fires during the window, the outcome is capped at
*directionally supported* and recorded as "supported with confound noted" —
which does **not** satisfy the isolated-evidence requirement. Before the delta
review, reconcile `git log -- src/components/content/HomePage.astro
src/i18n/content/en/index.json src/i18n/content/es/index.json
src/data/news.ts` against the scope statement.
